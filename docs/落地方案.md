# Starcat Admin Console 落地方案

> 状态：Phase 1 本地版本已实现，并于 2026-08-24 通过自动化、浏览器及真实测试/生产服务人工验收。
>
> 项目路径：`supports/starcat-admin-console`

## 1. 项目目标

建设一个独立、开源、本地优先的 Starcat 运营控制台，用统一界面查看配套 API 的数据统计、
执行运营操作、管理服务配置，并承接精选项目发布和 Awesome 来源维护。

第一阶段的交付物是可在管理员本机启动的 Web 服务。打开页面后，可以明确切换测试与生产
环境，验证各服务数据和操作流程。第二阶段再讨论远程部署、身份认证与多用户权限。

## 2. 已确认范围

### 2.1 服务范围

- 六个业务服务：sharing、trending、weekly、wiki、recommend、discovery。
- 生产环境通过 `https://starcat-api.fly.dev` 和 `X-SC-Svc` 路由六个业务服务。
- 测试环境允许为六个服务分别配置本地 URL 和 Key，适配独立启动的开发方式。
- 生产环境六个服务共享一把 API Key；Weekly 与 Discovery 额外使用各自的 Admin Key。
- 测试环境按服务配置 API Key，只有 Weekly 与 Discovery 提供 Admin Key 配置。
- 控制台只管理上述六个开源业务服务，不接入任何闭源服务。

### 2.2 管理能力

- Dashboard：服务健康、核心数据量、最近任务、缓存状态和异常摘要。
- 服务详情：统计指标、最近请求或任务、服务提供的明确操作。
- 数据操作：刷新缓存、清空缓存、新增数据、重跑任务等类型化动作。
- 配置中心：测试与生产 Profile、服务 URL、Key 状态、Agent Provider、Fly 配置。
- Awesome 来源：查看、新增、修改、删除和启停来源；不管理内置 README 内容。
- 精选发布：从自然语言、链接或混合清单开始，经 Agent 识别与人工审阅后发布。
- 高级运维：保留 Fly 环境变量和 Secrets 管理入口。

### 2.3 明确不做

- 第一阶段不远程部署，不做登录、RBAC、多租户和公网访问。
- 不提供通用数据库编辑器，不允许绕过 API 直接修改 SQLite。
- 不管理 Awesome 内置 README 条目。
- Agent 不自动发布数据，也不持有 Weekly 管理密钥。
- Web 控制台未通过功能对齐和人工验收前，不下线现有精选发布台与 `_local-admin`。

## 3. 信息架构

| 一级导航 | 页面 | 核心内容 |
|---|---|---|
| Overview | Dashboard | 全局统计、服务健康、最近任务、异常和快捷操作 |
| Services | Service Detail | 六个开源业务服务的状态、指标、缓存和类型化动作 |
| Data | Curated Imports | Agent 识别、证据审阅、分类选择与幂等发布 |
| Data | Awesome Sources | Awesome 来源的增删改查、启停和同步状态 |
| Operations | Jobs & Activity | 缓存任务、同步任务、批次状态和可审计结果 |
| Tools | API Explorer | 受控的已登记接口调试，不提供任意 URL 请求 |
| Settings | Profiles | Test / Production URL、Key 状态和连通性检查 |
| Settings | Agent | Provider、Model 和网络核验策略 |
| Settings | Fly | App、环境变量与 Secrets 的高级运维入口 |

页面顶栏始终展示环境切换器。测试环境使用蓝绿色标识，生产环境使用橙红色标识，并在所有
写操作确认层重复展示当前环境，避免仅依赖颜色判断。

## 4. 技术方案

### 4.1 前端

- React + TypeScript + Vite。
- shadcn/ui + Tailwind CSS，使用语义化主题 token。
- TanStack Router、TanStack Query 与按页面动态加载。
- 浏览器使用受控表单，BFF 使用 Zod 校验配置与写入 payload。
- shadcn Table 展示高密度运维数据，Lucide 提供图标。

控制台采用桌面优先的响应式布局：可折叠侧边栏、固定环境状态区、信息密度适中的统计卡片、
表格和审阅工作台。视觉上强调清晰层级、留白和状态表达，不复制旧发布台的三等分窗口样式。

### 4.2 本地 BFF

使用 Node.js 运行时和 Hono 构建 Backend for Frontend。浏览器只访问同源 BFF，BFF 负责：

- 保存与读取本地 Profile；
- 注入服务 Key、`X-SC-Svc` 和 Fly 凭据；
- 将不同服务的响应转换成统一 envelope；
- 代理 Agent、GitHub 网络核验和 Fly 操作；
- 前端会话记录脱敏后的本地操作历史。

服务默认绑定 `127.0.0.1`，校验 Host 和 Origin。Key、Token 和 Fly 凭据不返回明文，前端只
显示“已配置 / 未配置”和不可逆指纹。凭据不进入 localStorage、URL、日志或错误 payload。

### 4.3 服务适配层

每个服务通过 adapter registry 描述以下能力：

- 健康检查与版本信息；
- 统计指标及展示格式；
- 允许执行的动作、参数 schema 和风险等级；
- Test Profile 的本地地址；
- Production Profile 的 gateway header 或独立地址。

这种设计允许页面共享骨架，同时保留各 API 的真实差异。控制台不会提供任意 URL、Method
和 Body 的通用生产请求入口。

## 5. 环境切换与生产写入

### 5.1 Profile

- **Test**：连接本机分别启动的服务，URL 与 Key 可按服务配置。
- **Production**：六个开源业务服务连接聚合网关并共享 API Key；Weekly 与 Discovery 的
  管理操作分别使用独立 Admin Key。
- 切换后清空当前 Query Cache 并重新拉取，未提交表单不跨环境保留。
- 页面标题、顶栏 Badge、写操作确认层和操作记录同时标记当前环境。

### 5.2 写入原则

生产环境直接允许写，不增加全局 Production Writes 开关。以下动作仍需针对本次操作确认：

- 清空缓存、删除来源、覆盖配置等破坏性操作；
- 批量发布、批量重跑等影响范围较大的操作；
- Fly Secrets 的新增、覆盖和删除。

确认层展示目标服务、环境、对象数量和不可逆影响。请求结果不明确时复用原 payload 与
idempotency key 查询或重试，避免重复写入。

## 6. Agent 精选导入

Web 版沿用已验证的固定流水线，而不是把粘贴内容直接转换成 API 请求：

1. **线索拆分**：LLM 将自然语言、项目名、链接和混合清单拆成候选线索。
2. **受限检索**：对候选执行有上限的 GitHub 搜索，获取 canonical repository、搜索依据
   和必要的 README 摘要。
3. **证据判断**：LLM 依据真实候选给出 `confirmed`、`needs_review` 或 `not_found`；不得生成
   未经核验的仓库地址。
4. **人工审阅**：管理员查看证据、修正仓库、排除项目并选择来源分类。
5. **显式发布**：仅发布已确认且选中的项目；需要时先读取或创建 manual source。
6. **终态轮询**：以稳定 idempotency key 提交整个批次，并轮询到成功或失败终态。

识别模块只获得 AI 和检索能力，不获得 Weekly 管理密钥；发布模块只接收人工确认后的结构化
候选。粘贴文本、检索摘要和 README 片段可能发送给配置的 AI Provider，发起前必须在 UI
明确提示这一数据边界。

## 7. Awesome 来源管理

Awesome 页面管理 Discover 新接口暴露的“来源”对象，字段以服务最终契约为准，预计包括：

- 标识、名称、简介、图片或图标；
- 来源 URL、分类和排序；
- 启用状态、同步状态、最近同步时间和错误摘要。

支持列表、详情编辑、新增、语义归档、发布和手动同步。README 内容与内置项目条目不在本
控制台编辑，避免同时维护两套内容来源。

## 8. 测试与验收

### 8.1 自动化验证

- Vitest：配置存储、密钥脱敏、服务注册表、Fly 路由、精选导入路由和环境上下文。
- React Testing Library：浏览器环境上下文与环境切换持久化。
- Playwright：环境切换、响应式导航、主题持久化和两套环境凭据矩阵。
- 构建检查：Prettier、ESLint、TypeScript、生产构建和生产依赖审计。

### 8.2 第一阶段验收标准

- 使用文档中的单一命令在本机启动 Web 与 BFF。
- 页面可切换 Test / Production，且全局能明确识别当前环境。
- 六个开源业务服务能展示健康状态与已有统计。
- Test 可配置各本地服务，Production 可配置聚合网关。
- 可执行服务已支持的缓存与数据操作，并获得明确结果。
- 可从粘贴文本发起 Agent 分析、联网核验、人工审阅并发布精选项目。
- 可完成 Awesome 来源的新增、修改、删除、启停和同步验证。
- 可维护 Fly 环境变量与 Secrets，浏览器和日志中不泄露凭据。
- 自动化测试通过，并完成一次测试环境与一次生产环境人工验收。

## 10. 旧入口下线条件

以下条件全部满足后，才进入下线变更：

1. Web 精选导入覆盖现有三阶段能力并通过自动化测试。
2. dong4j 完成测试与生产环境的人工发布验收。
3. Web 控制台具备可用的失败恢复、幂等提交和操作记录。
4. 再单独提交 Starcat App「精选发布台」和 `_local-admin` 下线方案并征求确认。

下线属于独立任务，不与控制台初版实现混在同一提交。Starcat 根项目文档和
`docs/功能实现总览.md` 只有在 dong4j 明确授权后才同步更新。
